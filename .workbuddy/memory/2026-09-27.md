## RAGLite 实测基准（为简历收集真实数据）

- 环境：Windows，Python 3.11（uv venv），DuckDB 1.5.5，Raptor Lake 24 逻辑核。
- 网络坑：huggingface_hub 经 hf-mirror 下载恒为 0 字节 → 手动 curl 构造 HF 缓存（FacebookAI/xlm-roberta-base tokenizer.json、segment-any-text/sat-1l-sm model_optimized.onnx + config.json）；FlashRank zip 手动解压到 user_data_dir("raglite")；PyPI 换清华镜像；numpy 1.26.4 无 py313 wheel → 用系统 Python 3.11。
- 实测数据（scripts: bench_resume.py / fill_and_search.py / fill_and_search.py 产物 bench_results.json + bench_log.txt）：
  - 切分（96106 字符 specrel×2）：SaT ONNX 句切分 2.90s、chunklet DP 93ms、BIP 语义分块 14ms（714 句→198 chunklets→58 chunks）。
  - 索引（1000 chunks / 10000×1536）：HNSW 构建 26.6s（文件库）/14.0s（内存）、FTS(BM25) 0.66s。
  - 检索（单连接稳态）：精确向量扫描 P50 46.5ms（内存）/~75ms（文件库）、BM25 top-20 P50 17.5ms、RRF 0.01ms、chunk spans 组装 57.6ms、FlashRank 重排 20 候选 P50 923ms。
- 两个重要发现（可作面试 talking points）：
  1. DuckDB VSS 的 HNSW 索引扫描未命中（EXPLAIN 验证，持久化与内存模式皆未命中该形状的 plan），实际执行的是暴力精确扫描。
  2. raglite insert_documents 走 SQLAlchemy flush + FLOAT[1536] 参数绑定时单文档 ~480s（mock embedding 下），executemany 同样病态；用 Parquet 批量导入 10000 向量仅 127s 且构建索引后检索正常。
  3. vector_search 端到端 ~6.3s 为伪影（每查询连接级索引加载），不代表检索引擎能力。
- 未测：本地量化 embedding/生成模型推理延迟、端到端 RAG 生成、评测集准确率（需 LLM）。

## 补充（同日晚些）：复现指南 + SaT 数字的可信度问题

- 新建 `复现指南-实测数据.md`：逐步复现命令（切分 / 建库检索 / EXPLAIN 验证 / 换机完整搭建 / 未测项补测清单）。
- **重要发现：SaT 切分段对机器负载极度敏感。** 同一份代码、同一份 `bench_markdown.txt`：
  - 09-27 空载：`split_sentences_ms` ~= 2902
  - 09-27 晚些 load=68 重测：`split_sentences_ms` = 11182（chunklet 180ms / BIP 30ms 仍接近原值）
  - OMP_NUM_THREADS = 1 / 4 / 24 结果几乎不变（9.9-10.1s）→ 不是线程调度问题，是单核算力被抢
  - 佐证：30M 次 Python 空循环从 ~1000ms 涨到 ~1750ms，单核吞吐掉约 45%
- 结论：简历引用「切分 2.9s」必须连同测试机与负载一起注明，否则面试时被问「为什么换台机器跑就不一样」无法自辩。后续任何数字都建议先打环境指纹（load + 单核微基准）。
- 修正 EXPLAIN 命令：`EXPLAIN` 返回的物理计划在**第 2 列**，第 1 列只是字段名 `physical_plan`。本轮实测 plan 为 HASH_JOIN + ORDER_BY(array_distance(...)) 全量扫描，无 `USING HNSW`，与先前结论一致。
- 坑：`/proc/loadavg` 只能在 Git Bash 里用 `cat` 读；Windows 原生 Python 会把路径解析成 C:\proc\loadavg，打开失败。

- 两个新确认的坑（教程已写，均经无模型脚本核实）：
  1. `RAGLiteConfig` 默认 reranker 工厂在首次构造时会联网下载 MultiBERT（en 已缓存、other 未缓存），离线必报 ProxyError → 离线必须传 `reranker=None`（基准脚本即如此）。
  2. 默认 `search_method` 是纯向量 `_vector_search`，**不是**混合检索；README 「applies hybrid search」与代码不符。要做混合+重排需 `replace(config, search_method=search_and_rerank_chunk_spans)`。
- LiteLLM 初始化会尝试联网拉 cost map，超时回退本地，仅警告无害。
- 已验证：显式字符串 config + `reranker=None` 可构造；`Document.from_text` / `replace` 正常；全部公开 API 可导入。
